2. Purpose

- This app is designed to help students manage their own schedules and those of their friends. It supports not only personal schedules but also schedule sharing and collaboration.

- In the initial client report from week 4, the client needed an intuitive scheduling tool that would allow students to easily view each other's schedules and their own. Specifically, the client wanted a calendar system that was accessible on both mobile and computer, with an uncomplicated interface and a clear visual structure.

- To meet these needs, SyncSpace is designed to manage personal accounts through a login system and share calendars with groups of friends. It also offers a day view feature that allows users to easily check their schedules for specific dates and a function that calculates common free time across multiple users' schedules. This allows students to more efficiently plan group activities and study time.

3. Data Description

1 - USERS

Why it is needed: This table is needed to store each person who can log in and use the calendar system.

What it stores: It stores account and identity information for each user.

- Fields

  • user_id — INT — Primary Key
  • username — VARCHAR(50)
  • email — VARCHAR(100)
  • password_hash — VARCHAR(255)
  • created_at — DATETIME

2 - GROUPS

Why it is needed: This table is needed to represent shared groups that have their own calendars.

What it stores: It stores basic information about each group, such as its name and who created it.

- Fields

  • group_id — INT — Primary Key
  • group_name — VARCHAR(100)
  • description — TEXT
  • created_by — INT
  • created_at — DATETIME

3 - GROUP_MEMBERS

Why it is needed: This table is needed because one user can belong to many groups, and one group can contain many users.

What it stores: It stores the membership relationship between users and groups, along with each member's role.

- Fields

  • membership_id - INT - Primary Key
  • group_id - INT
  • user_id - INT
  • role - VARCHAR(20)
  • joined at - DATETIME

4 - EVENTS

Why it is needed: This table is needed to store all calendar events, whether they belong to a user’s personal calendar or a group calendar.

What it stores: It stores event details such as title, description, start and end times, creator, and ownership.

- Fields

  • event_id - INT - Primary Key
  • title - VARCHAR(100)
  • description - TEXT
  • start_time - DATETIME
  • end_time - DATETIME
  • created_by - INT
  • owner_user_id - INT - nullable
  • owner_group_id - INT - nullable
  • location - VARCHAR(150)
  • is_all_day - BOOLEAN
  • created_at - DATETIME
  • updated_at - DATETIME
  • anonymous - BOOLEAN
  • importance - INT

5 - RECURRING_EVENT

Why it is needed: This table is needed to store the repetition pattern for events that occur regularly, such as daily, weekly, or monthly events.

What it stores: It stores recurrence rules linked to an event, including how often it repeats and when the repetition ends.

- Fields

  • recurring_id - INT - Primary Key
  • event_id - INT
  • repeat_type - VARCHAR(20)
  • interval_value - INT
  • days_of_week - VARCHAR(20) - nullable
  • end_date - DATETIME - nullable
  • occurrence_count - INT - nullable

6 - EVENT_EXCEPTIONS

Why it is needed: This table is needed to handle special cases where one occurrence of a recurring event is changed, skipped, or cancelled without changing the entire series.

What it stores: It stores modifications for individual occurrences of recurring events, such as a different time, a cancellation, or a changed title.

- Fields

  • exception_id - INT - Primary Key
  • recurring_id - INT
  • original_date - DATETIME
  • is_cancelled - BOOLEAN
  • new_start_time - DATETIME - nullable
  • new_end_time - DATETIME - nullable
  • new_title - VARCHAR(100) - nullable
  • new_description - TEXT - nullable

4. Functions Performed by the App

1 - User Registration and Login

  • Users can create an account and log into the system to access their personal and shared schedules.
  • Database Effect
    • INSERT into USERS when a new account is created
    • SELECT from USERS to validate login credentials

2 - Create and Manage Personal Events

  • Users can create events in their personal calendar, including title, time, location, and description.
  • Users can optionally mark events as anonymous.
  • Anonymous events hide all details except time and priority when viewed by others.
  • Database Effect
    • INSERT into EVENTS when a new event is created
    • UPDATE on EVENTS when an event is edited
    • DELETE from EVENTS when an event is removed
    • INSERT & UPDATE EVENTS with anonymous_flag (if event is anonymous)

3 - View Calendar (Daily / Weekly / Monthly)

  • Users can view their schedule in different formats (day, week, or month), with events clearly displayed.
  • Responsive design supports both desktop and mobile devices
  • Database Effect
    • SELECT from EVENTS to retrieve relevant event data
  • Client-side Implementation
    • JavaScript dynamically renders calendar views
    • Events are visually organized with clear hierarchy and minimal clutter

4 - Create and Manage Groups

  • Users can create groups to share schedules with others and collaborate.
  • Database Effect
    • INSERT into GROUPS when a group is created
    • INSERT into GROUP_MEMBERS when users are added to a group
    • DELETE from GROUP_MEMBERS when users leave or are removed

5 - Share Events with Groups

  • Users can assign events to a group so all members can view them.
  • Database Effect
    • INSERT / UPDATE in EVENTS using owner_group_id
    • SELECT from GROUP_MEMBERS to determine access permissions

6 - View Other Users' Schedules

  • Users can view the schedules of group members to coordinate activities.
  • Database Effect
    • SELECT from EVENTS based on group membership
    • SELECT from GROUP_MEMBERS to verify access
  • Client-side Implementation
    • Events from different users are visually distinguished (e.g., color or labels)

7 - Daily Comparison View

  • Users can select a specific day to compare schedules and see availability across multiple users.
  • Shows distribution of event priorities across users for the selected day.
  • Database Effect
    • SELECT from EVENTS filtered by date and users
  • Client-side Implementation
    • JavaScript filters and displays only relevant time blocks for the selected day

8 - Free Time Finder

  • The app calculates shared free time between users to help schedule meetings or study sessions.
  • Supports priority-based scheduling (events have importance levels).
  • Displays which users are busy and affected in each time slot.
  • Provides two optimization modes:
    • Minimize number of people inconvenienced
    • Minimize total inconvenience (based on event priority)
  • Database Effect
    • SELECT from EVENTS for all selected users (including importance field)
  • Client-side Implementation
    • Algorithm compares time intervals to find overlapping free slots
    • Evaluates trade-offs between time slots using priority weights

9 - Recurring Events

  • Users can create events that repeat daily, weekly, or monthly.
  • Database Effect
    • INSERT into RECURRING_EVENT
    • SELECT to generate repeated occurrences

10 - Modify or Skip Recurring Events

  • Users can modify or cancel specific instances of recurring events
  • Database Effect
    • INSERT into EVENT_EXCEPTIONS
    • UPDATE based on exception rules

11 - Offline Viewing (Cached Data)

  • Users can view previously loaded schedules even without an internet connection.
  • Database Effect
    • No direct database interaction while offline
    • When online: SELECT data for caching
  • Client-side Implementation
    • Data is stored locally on the device and rendered without server access

12 - Event Importance (Optional Optimization Feature)

  • Users can assign importance levels to events to assist in scheduling decisions.
  • Database Effect
    • UPDATE / INSERT within EVENTS (if importance field is included)
  • Client-side Implementation
    • Used in scheduling logic to prioritize important events when calculating free time

13 - Import Schedule from Mosaic

  • Users can import class schedules from McMaster Mosaic to avoid manual input.
  • Database Effect
    • INSERT into EVENTS from parsed timetable data
  • Client-side Implementation
    • Parser extracts course time blocks and automatically creates events

8. Client Feedback

  • “Why don't we add the function to make an event anonymous? It can appear as a blocked out area with priority”
    • An event can have an anonymous tag, where when it is pulled from the database, all information is scrubbed aside from the time it takes up and the priority.
  • “Please make sure that the view does work on both the computer mobile”
    • We never explicitly wrote that the app would have the function to work on mobile and computer, this was added as a function.
  • “Could you find a way to import the class times from mosaic? My number one complaint with my calendar app was how long it took to input my classes”
    • We added a function that is able to look at the McMaster mosaic timetable and add them as events.
  • “It would be nice if it could show which people are free on which days, like 2 people are free on Tuesday, 1 person has a low priority task, and 1 person has a high priority task. When groups get big, a way to see the composition of priorities for a given day. There's probably situations where there's a perfect time, but if not we want to pick the next best thing”
    • Make sure that after finding time slots, we clearly display which events are taken up and who is inconvenienced. Also create 2 modes, minimum amount of people inconvenienced and minimum amount of total inconvenience. Added this into the free time finder description.
